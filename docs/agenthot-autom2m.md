# AutoM2M and AgentHOT: paper-to-code map

This document maps every concept, definition, algorithm and experiment of the paper
[`emse-autom2m.tex`](emse-autom2m.tex) to the code, and records the design decisions and known
deviations of the implementation. Version 0.4.0.

**Naming.** *AutoM2M* is the system and the main project (Python package `autom2m`, CLI `autom2m`,
Claude Code plugin `autom2m`). *AgentHOT* (Agent Hand-Off Transformations) is its execution layer, the
hand-off level: the compiler and the runtime (package `agenthot`, CLI `agenthot` for hand-written
teams, rule files `*.agenthot`, workspaces `.agenthot/`). AutoM2M sessions live in `.autom2m/`.
Environment variables of the runtime and service use the prefix `AGENTHOT_`.

## 5. Design decisions and deviations

- **Goal view.** As Listing 3, plus `Task.outline`: the class outline without doctests (the frame
  into which deliverables are inserted, and context class-level methods need). Doctests become
  `Example` objects keyed `E<i>.<j>`.
- **Reading the goal view.** A rule may navigate from its source objects into the read-only goal
  view (e.g. `d.method.signature` in `Design2Impl`), as the paper's admitted DevTeam does; reads into
  any other non-source view are W1 violations.
- **Validator reads per class.** `test_valid` reads `m.signature, m.examples.call, m.examples.expected`
  of a `Method`; on another goal class (the requirements team) it reads the object's attributes and
  those of its many-valued references.
- **One-sided W4** is reachability over production ∪ check edges. With Table 4's `test_valid`, whose
  argument reads the examples, it also misses the "detach" mutants of the hand-written teams (Table 7 in
  the paper reports them caught; those numbers came from an earlier validator library).
- **Totality.** Some anchoring chain must consist of rules whose source classes are total; guards that
  are neither implied by the scope nor joins only warn (paper: "warns about others").
- **Typed LLM values.** An LLM answers in text; values for `int` / `boolean` attributes are parsed, and
  an unparsable answer is a rejection. W1 rejects stochastic bindings to many-valued features.
- **Typed-NC compilation** (`compile_team(lenient=True)`): an ill-typed stochastic binding compiles to a
  footprint that raises, which the engine escalates without sampling; ill-typed structural bindings are
  dropped; ill-typed guards never match; at most three passes.
- **Replay seeds.** The Ollama backend derives a seed per call from the run seed, so replays and
  best-of-n samples are fresh samples while runs stay reproducible.
- **Attribution budget per repair round:** two root failures (escalations first), footprint
  minimisation at most eight probes.
- **RQ4 injection** starts every fault from a snapshot of one clean run and re-samples only what the
  fault makes stale. The validator fault replays the clean run's accepted values, so a rejection comes
  only from the flaky check; the sampling fault degrades every value of the owning agent with
  probability 0.6.
- **Auxiliary LLM roles.** The paper uses Qwen2.5-Coder 32B and Devstral as RQ3 coders, DeepSeek-Coder-V2
  as defect seeder, three critics and Qwen2.5-Coder 32B as attribution judge, and human coders for RQ1.
  Here every role is configurable (`evaluation/llms.py`); the runs so far use Qwen2.5-Coder 7B for all
  of them (two coders = the same model with different seeds and prompt variants), which inflates
  agreement and should be replaced by the paper's models and human coding for the final study.
- **No synthetic data.** The paper's `analysis/simulate.py` placeholders are not part of this package;
  every number comes from real logs.
