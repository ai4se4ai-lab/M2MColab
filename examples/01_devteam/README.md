# 01 — DevTeam (the paper's running example)

Four agents collaborate on a small backlog: **Analyst** (owns `Req`),
**Architect** (owns `Arch`), **Developer** (owns `Code`), **Tester** (owns
`Test`). This is the exact scenario from Fig. 1 and Sec III-B of
`docs/DS-A2A.tex`, including the `Story2Operation` listing verbatim.

```
Req --T1(Req2Arch)--> Arch --T2(Arch2Code)--> Code
 |                                                  
 +---------------T4(Req2Test)--------------------> Test
```

## What it demonstrates

| Mechanism | Where |
|---|---|
| Hybrid rule (structural + stochastic bindings) | `rules/Req2Arch.agenthot` — `Story2Operation` (`name`, `component` structural; `signature` stochastic with `@check`) |
| Trace-based reference resolution (Prop. 1) | `component <- s.epic` resolves through the trace to the `Component` generated by `Epic2Component`, *not* a copy of the source `Epic` |
| Footprint-bounded prompting | Every `@llm(prompt, footprint)` call only ever sees `footprint`'s value, never the whole model — see `agenthot.engine.binding._footprint_to_text` |
| Validator-gated acceptance (Prop. 3) | `@check signature.parses() and signature.params->notEmpty()`, `@check body.compiles()`, `@check oracle.failsOnStub()` |
| A guard filtering P1 hallucination/omission | `(s.status = #accepted)` — story `S3` is a draft and correctly gets **no** `Operation`, but still gets a `TestCase` from `Req2Test` (T4 matches `Criterion` directly, independent of T1) |
| The acceptance predicate phi | `runtime.acceptance_holds()` at the end of `run.py` |

## Run it

```bash
# from the repo root, with the venv active and `pip install -e .` done
python examples/01_devteam/run.py --llm mock       # no network needed
python examples/01_devteam/run.py                  # local Ollama (default; needs `ollama serve`)
python examples/01_devteam/run.py --llm ollama --model qwen3:8b
python examples/01_devteam/run.py --llm anthropic --model claude-haiku-4-5-20251001  # needs ANTHROPIC_API_KEY in .env
```

Expected output: a per-hand-off report (created/deleted/resampled/
escalations), the obligations discharged this run, the generated `Arch`,
`Code`, and `Test` models, and `Acceptance predicate phi holds: True`.

## Files

- `metamodels.py` — the four EMF/pyecore view metamodels (`Req`, `Arch`,
  `Code`, `Test`).
- `seed_models.py` — a small seed `Req` model (3 stories, one still a draft).
- `rules/*.agenthot` — the three hand-offs, in the DSL described in
  `docs/ARCHITECTURE.md`.
- `rules/helpers.py` — Python helpers the rules call (`toOpName`,
  `parses`, `params`, `compiles`, `failsOnStub`) — our stand-in for ATL
  `helper` blocks, imported via each module's `uses 'helpers.py';`.
- `run.py` — wires the four views into a `Team`, runs it to a fixpoint.

## Note on scope

The paper's Fig. 1 diagrams a fourth hand-off, Code→Test (`T3`), but gives
no listing for it in the text (only `T1`/`Req2Arch` and `T4`/`Req2Test` are
spelled out in Sec III-B). This example implements exactly the two
hand-offs the paper details, plus the natural `Arch2Code` hand-off needed
to populate the Developer's view — three hand-offs across all four
metamodels, without inventing content the paper doesn't specify.
